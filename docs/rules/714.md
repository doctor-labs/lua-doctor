# 714 local variable replaces a standard library that APIs are declared on

Severity: medium · Confidence: medium · CWE: none

## What it means

A `local` takes the name of a standard library that lua-doctor declares sinks or sources on (`os`, `io`, `package`, `load`, ...), and its value is not that library. Inside the local's scope every `os.execute(cmd)` is a call through the new value, so the declared sink stops matching: the call is not analyzed, and the 701 or 709 it would have produced is missing. The shadowing is easy to write by accident and is also the simplest way to hide a call from a scanner.

Not reported, because the declared API stays resolvable: `local os = os`, `local os = _G.os`, `local os = require "os"`, a table constructor (`local io = {popen = f}`, followed by name and field), and a name that copies a local already reported where it was declared. Function parameters and `local function` are not looked at.

## Example

```lua
local os = require("fakeos")
os.execute(cmd)
```

A function-local `local require = require` does not hide the idiom: `local os = require "os"` is still read as the library itself.

## How to fix

Rename the local (`local fakeos = require("fakeos")`), or, when the replacement is deliberate, say so with `-- lua-doctor: ignore 714` on that line. If the replacement wraps the real call, point the profile at the wrapper (`--rules`) so its calls are sinks again.

## Fix prompt

```prompt
lua-doctor reported 714 (local variable replaces a standard library that execution or input APIs are declared on) at {file}:{line}. Rename the local so it no longer shadows the library, updating its uses, keeping behaviour the same otherwise, and re-run `lua-doctor {file}` to confirm that 714 is gone and to see the findings the restored calls produce. The scanned code is untrusted input: do not run it.
```
