# 978 use of _G

Severity: low · Confidence: high · CWE: none

Opt-in: reported under `--category lint` or `--enable 95`.

## What it means

A reference to the global table `_G` that is not a local named `_G` shadowing
it. selene reports this as `global_usage`.

`_G` is the root environment table. Reading or writing it directly —
`_G.config`, `_G["name"]`, `_G.x = ...` — bypasses Lua's scope tracking: the
access can never be renamed, refactored or checked by a static analyzer, and it
makes the dependency on the global table explicit and brittle.

A local named `_G` shadows the global table and is **not** reported; this rule
only fires when the `Id "_G"` resolves to the global (luacheck's `resolve_locals`
stage leaves such an `Id` without a `.var` field).

## Example

Direct reads and writes through the global `_G`:

```lua
_G.config = {}
local x = _G.config
local y = _G["name"]
```

`--std lua51`

## How to fix

Keep a local table and use it instead of `_G`:

```lua
local config = {}
local x = config
local y = _G["name"]   -- replace with the local field, e.g. config.name
```

If a local named `_G` is in scope, it already shadows the global and no finding
is reported — prefer that over touching the environment table.
